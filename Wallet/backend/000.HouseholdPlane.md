# Household plane features

## Users management

The features for this section are configured for the household access, and not for regular users.
These features are:

- Creating, deleting, modifying, reading and listing users.
- Rotating the vault key, which means also resetting all the passwords for the users (the password
  is NOT reset for the household access, however). The new passwords are changed for all the users
  (this is done even for the soft-deleted ones) at random and returned in the response to be taken
  notes of. This can be done in two ways:
  - Generating a new vault recovery phrase.
  - Manually providing a custom vault recovery phrase. Same format of that on household creation.
- Changing the household password.

Notice how those actions need a logged session. The session is also validated to be between the
household only (a household endpoint described here will get a 401 if no valid session is used,
and a 403 if the session is not related to the household specified in the URL).

Also, special notes apply to vault key rotation. Vault key rotation makes sense since the account
is logged in, and hence the vault is loaded in-Redis by this point. The vault key rotation is the
mean to change the vault key without destroying the vault. In this case, the new stored vault is
changed to be encrypted with the new key (provided everything is valid). However, since it is not
possible to decrypt the internal copies of the users' vault keys, since they're encrypted by the
passwords of each user respectively, then all the passwords and vault key copies are destroyed and
need a manual password reset out of the temporary passwords created for them.

Please notice that losing somehow the vault phrase is something that cannot be recovered. It must,
in that case, be _rotated_.

Also, please notice that losing somehow the superuser password is also NOT recoverable. Alternatives
were discussed, but _this plane_ must not be the one in charge of dealing with the recovery / reset
of the household password. This is something that must occur in the master plane (it is already
documented there).

The REST interface for creating a user is:

    POST /$HOUSEHOLD_NAME/users
    Authorization: Bearer {session_id}

And the fields (body) are:

    // Please note that I'm adding these doc lines, which are not JSON-valid
    // but are up to you to understand what's needed.
    {
        // Mandatory data.
        "username": "my_username",
        "password": "My#P455W02D",
        "confirm_password": "My#P455W02D",
        "role": "adult" | "child" | "parent"

        // Optional data.
        "first_name": "John",
        "last_name": "Doe",
        "notes": "These are the notes for this user",
        "tags": ["some", "tags"]
    }

This will create the new user. Considering the following:

- The username will be converted to lowercase, trimmed, and expected to be like this:
  starting with a letter or underscore, allowed to contain letters, numbers, and underscore.
- Then, the username will be checked for uniqueness in the same household. Use indices as
  needed.
- The password and confirmation can be arbitrary, but they must match.
- The role must be among those 3 values.
- The username, the reference to the current household, the encrypted password, the role,
  and the optional fields are stored as the user's data. More fields can be described later.
  Notice how the POST payload accepts few different fields compared to what's stored (only
  the passwords are different).
- Please notice that not just the encrypted password is stored, but also an envelope is
  created for this user, using a key derived from the new password to encrypt the vault key
  for that user.

The error will be a 422 on bad / incomplete data. It will be 201 on success, returning all the
data (except for the password and vault key envelope) to the user, plus created_on / updated_on
fields, which are set automatically to the current date and time (as ISODate objects).

The REST interface for updating the user is:

    PATCH /$HOUSEHOLD_NAME/users/$username
    Authorization: Bearer {session_id}

And the fields (body) are:

    // Please note that I'm adding these doc lines, which are not JSON-valid
    // but are up to you to understand what's needed.
    {
        // All these fields are optional!.

        // Changing the username also involves reflecting the uniqueness criterion.
        "username": "my_username",

        // Updating the password also requires the confirmation. This is the way to
        // reset the password.
        password: "My#P455W02D",
        confirm_password: "My#P455W02D",

        // Then, any of the following data can be
        "role": "adult" | "child" | "parent"
        "first_name": "John",
        "last_name": "Doe",
        "notes": "These are the notes for this user",
        "tags": ["some", "tags"]
    }

Updating all the fields is trivial except for the password and confirmation. If they match,
the encrypted password is changed, but also the copy of the key is changed. It is done like
this:

- From the current session's associated vault, it is decrypted and the key is copied.
- Then, the key is enveloped for the user, using a key derived from the new password and
  encrypting the key with it.
- Finally, that envelope is stored in the user.

The answer is a 404, a 422 or a 200, typically. The 404 is also launched in the case the
user is soft-deleted. This is described next. It returns the full object (except for the
password and vault key envelope) in JSON format as a successful (200) response. Also,
a successful interaction causes `updated_on` to have the new timestamp.

The REST interface for deleting a user is:

    DELETE /$HOUSEHOLD_NAME/users/$username
    Authorization: Bearer {session_id}

The answer is a 404 or a 204. The deletion is logical. This means some extra fields must be
added to the user record: `created_on`, `updated_on` and `deleted_on`. Typically, created_on
and updated_on are safe to display everywhere and updated automatically, but `deleted_on` is
always null / unset unless the user is deleted. In this case, `deleted_on` serves to filter
when a user is deleted or not. This means that this field contributes to tell whether to
raise a 404 error or continue with the request (i.e. logical deletion).

The REST interface for reading a user is:

    GET /$HOUSEHOLD_NAME/users/$username
    Authorization: Bearer {session_id}

The answer is a 404 or 200 with the data. In this case, it must succeed even if the record is
soft-deleted (this is the only exception, along with the deleted-listing endpoint, to filter
rules on soft-deletion). The body will look like this:

    {
        "username": "my_username",
        "role": "adult" | "child" | "parent"
        "first_name": "John",
        "last_name": "Doe",
        "notes": "These are the notes for this user",
        "tags": ["some", "tags"],
        "created_on": ISODate(...),
        "updated_on": ISODate(...),
        "deleted_on": ISODate(...) or null
    }

Listing users is the next topic. There are two different lists, which return object in the
same format, but using a different filtering:

The REST interfaces are:

    GET /$HOUSEHOLD_NAME/users
    Authorization: Bearer {session_id}

and

    GET /$HOUSEHOLD_NAME/users/deleted
    Authorization: Bearer {session_id}

In both cases, the answer is a 200 code with an array of objects like this:

    {
        "username": "my_username",
        "role": "adult" | "child" | "parent"
        "first_name": "John",
        "last_name": "Doe",
        "notes": "These are the notes for this user",
        "tags": ["some", "tags"],
        "created_on": ISODate(...),
        "updated_on": ISODate(...),
        "deleted_on": ISODate(...) or null
    }

In the case of `/users`, focuses on the users in this household and only those that
are not deleted. Optional querystring arguments can be given:

- `skip`: The offset. If not given, not integer, or negative, it will use `0`.
- `limit`: The limit. If not given, not integer, or negative, it will use `10`.

In the case of `/users/deleted`, focuses on the users in this household and only those
that are deleted. Optional querystring arguments are the same.

Then, the next step is to define the password change:

    POST /$HOUSEHOLD_NAME/password-change
    Authorization: Bearer {session_id}

It expects a body like this:

    {
        "current_password": "my-password",
        "password": "new-password",
        "confirm_password": "new-password"
    }

The current password must match (i.e. able to perform a fake login). The new password and
the confirmation must match. If the three fields are the same, and everything is valid,
nothing is done in database by the end.

Also, the vault key is re-wrapped for this household user under the new password, to have
the consistent setting on the vault's key.

Finally, key rotation is different:

    POST /$HOUSEHOLD_NAME/rotate-vault
    Authorization: Bearer {session_id}

It takes a body:

    {
        "password": "current-password",
        "vault_recovery_phrase": "... 24 words ..."
    }

If the phrase is passed, it is validated to the format of a phrase (the 24 words and so).
Otherwise, a random key is generated server-side with very high entropy (e.g. /dev/urandom).
With this in mind, this is done:

1. All the users, deleted or not, are enumerated for that household.
2. The password is validated against the household. It must match.
3. The new key is derived from the vault recovery phrase and enveloped via the key that is
   derived from the password (yes: the password has purposes other than just validation).
4. The envelope is saved in the household.
5. Also, for each user, a new password is generated for them!! A simple, temporary, password.
   This forces the users to re-login as well (destroy all the sessions and the in-Redis
   encrypted vault key).
6. For each password, a key is derived and the new vault key is enveloped inside of it, for
   that user. Then, the record is saved.
7. Finally, the endpoint returns something like this:

       {
           // The passphrase, especially if it was generated, rather than provided.
           "vault_recovery_phrase": "... 24 words ...",

           // The new passwords:
           {
               "john": "aw8hdaw",
               "jane": "239qe923h",
               "dick": "jsjda00a2",
               ...
           }
       }
