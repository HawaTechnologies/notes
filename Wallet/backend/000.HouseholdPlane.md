# Household plane features

Many REST operations are defined here. They're for users management and vault management, but also
other things can be done (e.g. deploying ERC-4337 accounts).

Many operations affect the vault in some way. They generally need the operation flow described
in the main document (which implies: these operations are atomic in the household). Few operations
(e.g. user creation) might require no atomicity checks.

## Users management

The features for this section are configured for the household access, and not for regular users.
These features are:

- Creating, deleting, modifying, reading and listing users.
- Rotating the vault key, which means also resetting all the passwords for the users (the password
  is NOT reset for the household access, however). The new passwords are changed for all the users
  (this is done even for the soft-deleted ones) at random and returned in the response to be taken
  notes of. This can be done in two ways:
  - Generating a new vault recovery phrase.
  - Manually providing a custom vault recovery phrase. Same format of that on household creation.
- Changing the household password.

Notice how those actions need a logged session. The session is also validated to be between the
household only (a household endpoint described here will get a 401 if no valid session is used,
and a 403 if the session is not related to the household specified in the URL).

Also, special notes apply to vault key rotation. Vault key rotation makes sense since the account
is logged in, and hence the active vault root key is available through the session cache by this
point. The vault key rotation is the mean to change the vault key without destroying the vault. In
this case, the new stored vault is changed to be encrypted with the new key (provided everything is
valid). However, since it is not possible to decrypt the internal copies of the users' vault keys,
since they're encrypted by the passwords of each user respectively, then all the passwords and vault
key copies are destroyed and need a manual password reset out of the temporary passwords created for
them.

Please notice that losing somehow the vault phrase is something that cannot be recovered. Access
can still continue while the household password, a valid session, or user passwords can still unlock
the current vault root key, but the lost phrase itself cannot be retrieved. It must, in that case,
be _rotated_.

Also, please notice that losing somehow the superuser password is also NOT recoverable. Alternatives
were discussed, but _this plane_ must not be the one in charge of dealing with the recovery / reset
of the household password. This is something that must occur in the master plane (it is already
documented there).

The REST interface for creating a user is:

    POST /$HOUSEHOLD_NAME/users
    Authorization: Bearer {session_id}

And the fields (body) are:

    // Please note that I'm adding these doc lines, which are not JSON-valid
    // but are up to you to understand what's needed.
    {
        // Mandatory data.
        "username": "my_username",
        "password": "My#P455W02D",
        "confirm_password": "My#P455W02D",
        "role": "adult" | "child" | "parent",

        // Optional data.
        "first_name": "John",
        "last_name": "Doe",
        "notes": "These are the notes for this user",
        "tags": ["some", "tags"]
    }

This will create the new user. Considering the following:

- The username will be converted to lowercase, trimmed, and expected to be like this:
  starting with a letter or underscore, allowed to contain letters, numbers, and underscore.
- Then, the username will be checked for uniqueness in the same household. Use indices as
  needed.
- The password and confirmation can be arbitrary, but they must match.
- The role must be among those 3 values.
- The username, the reference to the current household, the encrypted password, the role,
  and the optional fields are stored as the user's data. More fields can be described later.
  Notice how the POST payload accepts few different fields compared to what's stored (only
  the passwords are different).
- Please notice that not just the encrypted password is stored, but also an envelope is
  created for this user, using a key derived from the new password to encrypt the vault key
  for that user.
- Tags are validated, each, to be lowercase words (i.e. only a-z letters or numbers, with
  optional single dashes between words, like `[a-z][a-z0-9]*(-[a-z0-9]+)*`). This is on
  creation or on update.

The error will be a 422 on bad / incomplete data. It will be 201 on success, returning all the
data (except for the password and vault key envelope) to the user, plus created_on / updated_on
fields, which are set automatically to the current date and time (as ISODate objects).

The REST interface for updating the user is:

    PATCH /$HOUSEHOLD_NAME/users/$username
    Authorization: Bearer {session_id}

And the fields (body) are:

    // Please note that I'm adding these doc lines, which are not JSON-valid
    // but are up to you to understand what's needed.
    {
        // All these fields are optional!.

        // Changing the username also involves reflecting the uniqueness criterion.
        "username": "my_username",

        // Updating the password also requires the confirmation. This is the way to
        // reset the password.
        "password": "My#P455W02D",
        "confirm_password": "My#P455W02D",

        // Then, any of the following data can be
        "role": "adult" | "child" | "parent",
        "first_name": "John",
        "last_name": "Doe",
        "notes": "These are the notes for this user",
        "tags": ["some", "tags"]
    }

Updating all the fields is trivial except for the password and confirmation. If they match,
the encrypted password is changed, but also the copy of the key is changed. It is done like
this:

- From the current session's associated vault, it is decrypted and the key is copied.
- Then, the key is enveloped for the user, using a key derived from the new password and
  encrypting the key with it.
- Finally, that envelope is stored in the user.

The answer is a 404, a 422 or a 200, typically. The 404 is also launched in the case the
user is soft-deleted. This is described next. It returns the full object (except for the
password and vault key envelope) in JSON format as a successful (200) response. Also,
a successful interaction causes `updated_on` to have the new timestamp.

The REST interface for deleting a user is:

    DELETE /$HOUSEHOLD_NAME/users/$username
    Authorization: Bearer {session_id}

The answer is a 404 or a 204. The deletion is logical. This means some extra fields must be
added to the user record: `created_on`, `updated_on` and `deleted_on`. Typically, created_on
and updated_on are safe to display everywhere and updated automatically, but `deleted_on` is
always null / unset unless the user is deleted. In this case, `deleted_on` serves to filter
when a user is deleted or not. This means that this field contributes to tell whether to
raise a 404 error or continue with the request (i.e. logical deletion).

The REST interface for reading a user is:

    GET /$HOUSEHOLD_NAME/users/$username
    Authorization: Bearer {session_id}

The answer is a 404 or 200 with the data. In this case, it must succeed even if the record is
soft-deleted (this is the only exception, along with the deleted-listing endpoint, to filter
rules on soft-deletion). The body will look like this:

    {
        "username": "my_username",
        "role": "adult" | "child" | "parent",
        "first_name": "John",
        "last_name": "Doe",
        "notes": "These are the notes for this user",
        "tags": ["some", "tags"],
        "created_on": ISODate(...),
        "updated_on": ISODate(...),
        "deleted_on": ISODate(...) or null
    }

Listing users is the next topic. There are two different lists, which return object in the
same format, but using a different filtering:

The REST interfaces are:

    GET /$HOUSEHOLD_NAME/users
    Authorization: Bearer {session_id}

and

    GET /$HOUSEHOLD_NAME/users/deleted
    Authorization: Bearer {session_id}

In both cases, the answer is a 200 code with an array of objects like this:

    {
        "username": "my_username",
        "role": "adult" | "child" | "parent",
        "first_name": "John",
        "last_name": "Doe",
        "notes": "These are the notes for this user",
        "tags": ["some", "tags"],
        "created_on": ISODate(...),
        "updated_on": ISODate(...),
        "deleted_on": ISODate(...) or null
    }

In the case of `/users`, focuses on the users in this household and only those that
are not deleted. Optional querystring arguments can be given:

- `skip`: The offset. If not given, not integer, or negative, it will use `0`.
- `limit`: The limit. If not given, not integer, or negative, it will use `10`.
- `tags`: Tags to search for. The entries having at least one of the tags among theirs are included.
  If the array is empty, it's as if it wasn't specified, and will not filter by tags. This
  is the default behavior.

In the case of `/users/deleted`, focuses on the users in this household and only those
that are deleted. Optional querystring arguments are the same.

Then, the next step is to define the password change:

    POST /$HOUSEHOLD_NAME/password-change
    Authorization: Bearer {session_id}

It expects a body like this:

    {
        "current_password": "my-password",
        "password": "new-password",
        "confirm_password": "new-password"
    }

The current password must match (i.e. able to perform a fake login). The new password and
the confirmation must match. If the three fields are the same, and everything is valid,
nothing is done in database by the end.

Also, the vault key is re-wrapped for this household user under the new password, to have
the consistent setting on the vault's key.

Finally, key rotation is different:

    POST /$HOUSEHOLD_NAME/rotate-vault
    Authorization: Bearer {session_id}

It takes a body:

    {
        "password": "current-password",

        // Optional field:
        "vault_recovery_phrase": "... 24 words ..." 
    }

If the phrase is passed, it is validated to the format of a phrase (the 24 words and so).
Otherwise, a new 24-word BIP-39 mnemonic is generated server-side with very high entropy (e.g.
from /dev/urandom). With this in mind, this is done:

1. All the users, deleted or not, are enumerated for that household.
2. The password is validated against the household. It must match.
3. The new key is derived from the vault recovery phrase and enveloped via the key that is
   derived from the password (yes: the password has purposes other than just validation).
4. The envelope is saved in the household. The vault is, obviously, encrypted with this new
   rotated key, derived from the rotated phrase provided or generated here.
5. Also, for each user, a new password is generated for them!! A simple, temporary, password.
   This forces the users to re-login as well (destroy all the sessions and the session-cached
   encrypted vault root key).
6. For each password, a new key is derived and the vault key is enveloped inside of it, for
   that user. Then, the record is saved.
7. Finally, the endpoint returns something like this:

       {
           // The passphrase, especially if it was generated, rather than provided.
           "vault_recovery_phrase": "... 24 words ...",

           // The new passwords:
           {
               "john": "aw8hdaw",
               "jane": "239qe923h",
               "dick": "jsjda00a2",
               ...
           }
       }

## Blockchain accounts management

Blockchain accounts must be managed here. Accounts are not just addresses but, also, their
underlying private keys. As of today we'll only support EVM networks, and we'll use the
secp256k1 curve (the only one available so far). So, in every case, we'll support the
following settings for a private key:

- Network type: EVM.
- Curve type: secp256k1.
- Its data: Only the hex. digits, like 0xab8cb2... the full private key.

Inside the encrypted vault, it'd look like this:

```json
{
    "network_type": "evm",
    "curve_type": "secp256k1",
    "name": "Some Name",
    "notes": "Lorem ipsum dolor sit amet ...",
    "tags": ["some", "tags"],
    "data": {
        "private_key": "0x..."
    },
    "address": "0x..."
}
```

> **Please note**: These are not separate records, but entries **in the encrypted vault**.
> This means that these operations are in-vault and, hence, all of them fall in the same
> household-scoped domain of atomicity. Also, the "address" is a field that must exist when
> all the data is validated (including: the private key is validated). This is a new field
> to add to the entry, and no two entries will exist with the same address in the same vault.

Aside from these, there are more fields like `created_on`, `updated_on` and `deleted_on`,
where all of them are ISODate fields and the `deleted_on` is optional (if `null`, the object
is not deleted, while if not `null` it is deleted).

The current version only allows `network_type` to be `evm` and `curve_type` to be `secp256k1`.
Future versions will implement more keys.

So far, we can say the vault, when decrypted, shows an object like this:

```json
{
    "accounts": [
        {
            "network_type": "evm",
            "curve_type": "secp256k1",
            "name": "Some Name",
            "notes": "Lorem ipsum dolor sit amet ...",
            "tags": ["some", "tags"],
            "data": {
                "private_key": "0x..."
            },
            "address": "0x..."
        },
        ...
    ]
}
```

> **Please note**: More fields might be added later for the vault spec. For now, only the accounts
> are being detailed, but there might be other sensitive cryptographic materials that would need
> their own top-level vault fields later.

This section describes many endpoints to update the "accounts" field in the vault. 
The endpoints are:

Creating the private key (with the said payload: network_type, curve_type, data, name, notes
and also tags - address is never included as a body field):

    POST /$HOUSEHOLD_NAME/private-keys
    Authorization: Bearer {session_id}

Returns a 201 (success) or 422 (validation error) response. The 201 response returns the full
object except for the private key (but created_on, updated_on and deleted_on are included).
Instead of showing the private key, it shows the address that is derived from the private key,
formatted to the supported network (`evm`, in this case, is the only network accepted).

All these fields are mandatory, although name and notes can be empty. The private key must be
validated against the network type and curve type. In this case, the only validation that will
exist is: checking the private key to be a 0x... hex. string in the secp256k1 curve field.

Also, the tags are validated, each, to be lowercase words (i.e. only a-z letters or numbers, with
optional single dashes between words, following format: `[a-z][a-z0-9]*(-[a-z0-9]+)*`). This is on
creation or on update.

Getting a private key (deleted or not):

    GET /$HOUSEHOLD_NAME/private-keys/$id
    Authorization: Bearer {session_id}

Returns a 200 with all the data (excluding the private key). Instead of the private key, it
shows its address. Returns a 404 instead if the account does not exist.

This GET endpoint works even if the private key / account is deleted.

Updating a private key is possible, but only to update tags, notes and name:

    PATCH /$HOUSEHOLD_NAME/private-keys/$id
    Authorization: Bearer {session_id}
    {
        "name": "New Name",
        "notes": "Some new notes go here",
        "tags": ["some", "other", "tags"]
    }

Both tags, name and notes are optional here. Tags are validated in the same way as of creation.

Deleting a private key is allowed only if the private key is not in use. It's executed like this:

    DELETE /$HOUSEHOLD_NAME/private-keys/$id
    Authorization: Bearer {session_id}

The possible responses are 204 on success, 404 on not found (or already deleted), or 409 if the
account / private key is already in use somewhere.

Then, there are other endpoints to manage private keys:

Getting the list of non-deleted keys:

    GET /$HOUSEHOLD_NAME/private-keys
    Authorization: Bearer {session_id}

Getting the list of deleted keys:

    GET /$HOUSEHOLD_NAME/private-keys/deleted
    Authorization: Bearer {session_id}

Both return an array as response (with code 200) and each entry in the array has the same shape
as the object in the individual GET endpoint. The difference between both is that the first uses
a check like `deleted_on is null` while the other one uses `deleted_on is not null`.

Both accept optional querystring arguments, which can be given:

- `skip`: The offset. If not given, not integer, or negative, it will use `0`.
- `limit`: The limit. If not given, not integer, or negative, it will use `10`.
- `tags`: Tags to search for. The entries having at least one of the tags among theirs are included.
          If the array is empty, it's as if it wasn't specified, and will not filter by tags. This
          is the default behavior.

> **Please note**: The front-end may create private keys however it chooses before submitting them.
> Options are (for the only supported curve and network types):
>
> - Manually specifying a private key, or generating it randomly with high entropy.
> - Generating a private key from a seed phrase (generated with high entropy in front-end, or manually
>   specified) and the account and address indices (i.e. using the HDWallet mechanism with a derivation
>   path like: m/44'/60'/{account}'/0/{index}).
>
> This is always considering that the back-end, on key creation, only accepts the final private key
> (at least, as of today and for evm/secp256k1 keys).

> **Please note, since this is quite important in terms of security**: Dealing with the vault means
> dealing with its decrypted text and its parsed JSON representation (maps, slices, and primitive
> values). Ensure that, for all the available means, every intermediate value is released from memory
> after the involved operations finish. This might involve something like zeroing all the byte arrays
> related to private key fields. No single trace of any private key must remain in memory.
