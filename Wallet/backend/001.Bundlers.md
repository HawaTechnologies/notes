# ERC-4337 Bundlers-related features

These features belong to the *master plane*, so they're container-space commands rather than
entry points. The idea is that the (stack) masters or owners can configure the bundlers that
are available for household accounts or their users to route the ERC-4337 transactions to.

## Bundler deployment

Bundler deployment is not covered here. A later definition in the stack may automatically,
via infrastructure actions, add containers (or pods) serving a specific bundler service,
tied to one or more (chain id, entrypoint contract address) pairs.

The important part is that bundlers serve the same JSON RPC API:

- eth_sendUserOperation
- eth_estimateUserOperationGas
- eth_getUserOperationByHash
- eth_getUserOperationReceipt
- eth_supportedEntryPoints
- eth_chainId

The implementation might be different per bundler. This includes knowledge of:

- The supported chain(s).
- The associated entry point contracts.
- The URL / path of the bundler, once mounted in an internal domain.
- The version of the bundler protocol.

Still, these bundlers will be managed by this stack and will follow the standard for bundlers
(ERC-7769) in terms of API (this means: it doesn't matter what are the available images out
there, as long as the protocol is respected, and we can identify its version and the other
already-stated fields).

## Bundler setup

At database level, this implies particular details. Just to start, if a bundle is not available
for a network, the immediate meaning is that the network cannot be used by any household in the
same ecosystem / node / replica set. This is because the main premise here is that the wallets
the users will have access to are ERC-4337 wallets (in terms of migration capabilities), rather
than EOAs.

But, also, setting up a bundler is not simple for end users (remember: this whole stack targets
regular households and not necessarily software developers), so typically a mater plane action
(typically: either automated one or UX-assisted managed by the owner of the stack) will take
place here. The important part is that each household will have a list of supported chains and
their bundlers at hand, but provided by the mater plane. For example, this could be set up in
a specific stack by their master plane:

```
# First, mainnets.
chain 1:
    bundler1
chain 8543:
    bundler1
    bundler2
chain 137:
    bundler3
chain 43114:
    bundler4

# Then, testnets.
chain 1115511:
    bundler1
chain 85432:
    bundler5
chain 80002:
    bundler3
chain 43113:
    bundler4
```

A simple bundler can serve many chains. Ideally, the master plane could also serve
many options of bundlers for a single network, and households may detect them being
available and with which priority they'd be chosen (inside a specific chain id) or
which policy of bundler picking will suit their needs (e.g. round-robin or other
scheduling algorithm). This design is to be determined, but the idea is that any
available bundler can be used for a chain id (considering the case where bundlers
can be maintained off and on by the master plane and households should never need
to refresh their own setup).

### Database and routing

Records will be added on database via master plane commands. First, the bundlers
will have the following fields in their collection:

- chain id: A number with the chain id.
- URL: The URL the bundler is mounted at.
- entry point: The address of the entry point in use.
- version: The version of the bundler / the entry point.
- created_on, updated_on, deleted_on: The timestamp fields, where deleted_on is
  optional and used to implement the soft delete mechanism.
- enabled: A boolean telling whether this bundler is enabled or not. Different to
  just deleting it, this field tells whether a bundler is listed (its existence
  is meant to be known about) but not selectable (at least, for now).

There are shell commands to set up the bundlers.
